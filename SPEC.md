# NRL Tipping App — Build Spec (v2)

Goal: upgrade the existing single-file app so it (1) refreshes NRL data automatically each
week from multiple sources, (2) uses a stronger, transparent prediction model, and (3) is
polished enough for a non-technical footy fan to use every round. The Roosters must always be
the locked tip.

Existing file: `nrl-tipping-guide.html` (works, seeded with end-of-Round-21 2026 data).

## Architecture

The app is opened as a LOCAL FILE (file://) in a browser. That constrains how data loads:
- A file:// page CANNOT `fetch()` a sibling JSON file (browser security blocks it).
- A file:// page CAN load a sibling `<script src="nrl_data.js">`.

So the data contract is a JavaScript file, not JSON:

### `nrl_data.js` (the data contract — DO NOT change shape without telling the team)
```js
window.NRL_DATA = {
  updated: "2026-07-27",          // ISO date the data was refreshed
  season: 2026,
  round: 22,                       // the ROUND TO TIP (next unplayed round)
  source: "zerotackle.com",        // where it came from
  teams: [
    // one per club, 17 total
    { name:"Roosters", short:"SYD", P:18, W:13, L:5, PF:449, PA:364, last5:4 }
    // last5 = number of wins in the club's last 5 games (0-5)
  ],
  fixtures: [
    // the games for `round`, home first. `odds` supports opening+closing
    // decimal-odds snapshots for closing-line-value (CLV) tracking:
    //   odds: { open: {home,away} | null, close: {home,away} | null }
    // The legacy flat `{home,away}` shape (one snapshot, no open/close) and
    // `null` are BOTH still accepted everywhere (parser + validator) for
    // backward compatibility with older nrl_data.js files.
    { home:"NQL", away:"SYD", venue:"QLD Country Bank Stadium", kickoff:"2026-07-30T09:50:00Z",
      odds: { open: {home:1.85, away:1.95}, close: {home:1.75, away:2.05} } }
  ],
  byeTeams: ["MAN"],
  results: [                       // OPTIONAL full-season match log — see note below
    { round:1, home:"PEN", away:"CBR", hs:24, as:12 }
  ]
};
```

### Opening + closing odds (CLV)

On a **full rebuild** (`parse_nrl.py` without `--merge`), a fresh odds dump sets both
`odds.open` and `odds.close` to the same freshly-parsed values (it's the only sighting so far).
On a **daily/gameday `--merge` run**, `open` is set the FIRST time odds are seen for a fixture
and is never overwritten again; `close` is updated to the newest parsed odds every merge run.
Comparing the model's read against `open` vs `close` is what makes closing-line-value (CLV) —
the honest yardstick for whether a tip beat the market — measurable. No new CLI flags are
needed; running the merge as usual now populates both fields.

### On `results[]` and Elo — current reality, not aspiration

> implemented — see the new section for the current, accurate picture.

`results[]` (an optional full-season match log) is defined in the schema, but **no parser or
front-end code currently populates or consumes it for an Elo/Glicko replay.** Earlier drafts of
this spec implied an Elo replay was active whenever `results[]` was present — that was never
actually wired up in the shipped front-end, and this doc was wrong to imply otherwise. A full
Elo/Glicko replay and historical backtest remain **FUTURE work** that requires a stored
season match-log; see "Current shipped model" below for what actually runs today.

## Learning loop (v4)

The app now has a genuine learning loop, distinct from the hand-tuned formula described above.
Each update, a new sibling file **`nrl_learned.js`** (`window.NRL_LEARNED`, generated by
`learn_model.py` from `nrl_data.js`'s `results[]` match log) stores the app's learned memory:

```js
window.NRL_LEARNED = {
  updated: "2026-07-27",
  gamesLearned: 137,          // how many completed games the fit is based on
  lowConfidence: false,       // guardrail flag — see below
  params: {                   // re-fitted dials, replacing hand-picked constants
    homeAdv: 3.2,              // points
    logisticScale: 7.0,        // points (margin -> win-probability steepness)
    oddsWeight: 0.35,          // 0..1, how much the market blend is trusted
    eloK: 20,                  // Elo K-factor
    eloHGA: 55                 // Elo home-ground-advantage, in Elo points
  },
  elo: { PEN: 1612.4, SYD: 1543.1, /* ...all 17 team shorts */ },
  backtest: { games: 137, brier: 0.211, logloss: 0.552, hit: 0.618, marketBrier: 0.198 },
  history: [ { date: "2026-06-01", games: 90, brier: 0.231 }, /* one snapshot per past run */ ],
  results: [ { round: 1, home: "PEN", away: "CBR", hs: 24, as: 12 }, /* the match log it learned from */ ]
};
```

- **Memory:** every completed result ever logged (via `nrl_data.js`'s `results[]`) feeds the
  fit — the app is not just reacting to this week's ladder, it remembers the whole season (and
  can, in principle, carry over between seasons).
- **Fitting:** `homeAdv`, `logisticScale`, and `oddsWeight` are re-estimated from that match log
  each update (replacing the previously hand-picked constants), and a standard Elo rating
  (`eloK`/`eloHGA` params, one rating per team in `elo{}`) is replayed from the full match
  history, sorted by round, so the result is deterministic regardless of how the log is stored.
- **Backtesting:** after each refit, the model backtests itself walk-forward over the match log
  (`backtest.brier`, `.logloss`, `.hit`, and `.marketBrier` when odds history exists) and keeps a
  `history[]` trend of past snapshots, so calibration drift over the season is visible, not just
  this week's numbers.
- **Guardrail:** `lowConfidence` is true (and the front-end should prefer the older hand-tuned
  formula) until roughly **30 games** of match history have been backtested — early-season fits
  on a handful of games are noisy enough that they shouldn't be blindly trusted. `gamesLearned`
  is what the app checks against that threshold.
- **Front-end:** the app shows a **"what it's learned" panel** — the current params, Elo ladder,
  backtest numbers, and the low-confidence badge when applicable — so a user can see not just
  this week's tip but why the model believes what it believes.
- **Elo is NOW implemented** — the "future work" language elsewhere in this document describing
  Elo as unbuilt is superseded by this section.

## File ownership (avoid edit collisions)

- **Dev A (data pipeline):** `parse_nrl.py`, `nrl_data.js` (generated output + a committed
  sample), `sources.md`. Do NOT touch the HTML.
- **Dev B (front-end/model):** `nrl-tipping-guide.html` ONLY. Load `window.NRL_DATA` if present,
  else use the embedded seed as fallback. Improve model + UX.
- **Dev C (QA/tooling/docs):** `validate_data.py`, `validate_learned.py`, `smoke_test.mjs`,
  `README.md`, `WEEKLY_UPDATE.md`, `SPEC.md`. Do NOT touch the HTML, the parser, or
  `learn_model.py`.

## Dev A — weekly data pipeline
- `parse_nrl.py` reads RAW page text/HTML saved to disk (fetched by the orchestrator via the
  web tools — the script itself must NOT make network calls) and emits a valid `nrl_data.js`.
- Support at least TWO sources for resilience (e.g. Zero Tackle ladder + NRL.com draw), and
  cross-check team counts / points. Degrade gracefully if one source is missing.
- Derive `round` = lowest round number with unplayed fixtures. Compute `last5` from results.
- Emit `byeTeams` (the club with no fixture that round).
- Validate before writing: exactly 17 teams, every fixture references known shorts, no team
  appears twice in a round.
- `fixture.odds`: on a full rebuild, a fresh odds dump sets `open` and `close` to the same
  values; in `--merge` mode, `open` is only ever set on first sighting (never overwritten),
  `close` always advances to the newest parsed price. Legacy flat `{home,away}` and `null` are
  still accepted on read.

## Dev B — front-end + model

**Current shipped model (post pro-tipper-panel review):** season points-margin, blended with
home/away-split margins and **shrunk toward the league average for small sample sizes**
(shrinkage weight ≈ P/(P+k)), plus a recent-form nudge (last-5), a **spine-weighted injury
penalty** (derived from the `team.news` free text — a halfback/hooker/fullback ruled out costs
more than a bench forward), a home-ground edge, and an **optional bookmaker-odds blend**
(de-vigged market probability, weighted against the model's own probability). This is a
transparent, hand-tunable formula — **not** Elo/Glicko.

- Data loading: use `window.NRL_DATA` when available; otherwise the current embedded seed.
  Show the "updated" date and source in the header. Never crash if data missing.
- **Probability logging + calibration:** log each game's predicted `pHome` (not just the tip),
  and track **Brier score** and a calibration view across the logged season so the app can say
  whether it's actually well-calibrated, not just "went 6/8".
- **CLV-aware odds:** `fixture.odds` now carries `open` (first sighting) and `close` (latest)
  decimal-odds snapshots; the odds blend uses the closing price (the more informative, final
  market read) when available, falling back to the legacy flat shape, else no market blend.
- **Comp-format modes:** a setting for win-only vs margin vs confidence/streak comps — margin
  comps surface the model's predicted margin; confidence comps rank tips by probability.
- **Roosters-tax stat:** a season-running figure for tips notionally lost by the locked Roosters
  pick versus what the model would have tipped, so the loyalty rule's real cost is visible.
- **Upset-of-the-week:** flags the game closest to 50/50 each round.
- Roosters lock preserved + the safe/risky verdict banner.
- UX polish: mobile-friendly, readable contrast, per-game one-line rationale, a saved
  tip-history + running accuracy tracker (how the model AND the locked-Roosters strategy have
  done), and the weekly result-logger. Persist in localStorage. No external CDNs required.
- **Elo replay + backtest — SUPERSEDED, now implemented:** this used to read "future work (not
  yet built): a full Elo/Glicko replay of the season and a historical backtest against real
  results." That is no longer accurate — see "Learning loop (v4)" above: `learn_model.py`
  replays Elo from `results[]` and backtests the fit every update, exposed to the front-end via
  `nrl_learned.js`, with a `lowConfidence` guardrail below ~30 games.

## Dev C — QA/tooling/docs
- `validate_data.py`: assert the data contract (17 teams, fixtures valid, dates parse, etc.);
  exit non-zero on failure. Reusable by the weekly job. Accepts `fixture.odds` as `null`, the
  legacy flat `{home,away}` shape, or the `{open,close}` CLV shape (numeric odds >1 on either
  side); emits a friendly INFO when both `open` and `close` are present (CLV trackable).
- `smoke_test.mjs`: load the model logic (Node) with a fixture dataset and assert tips compute,
  probabilities are 0-1, Roosters always tipped, byes handled. Runnable with `node`. Also
  mirrors the front-end's odds→probability helper (`marketProb()`: use `close` when present,
  else legacy flat, else null) and asserts it stays within [0,1] or null for all odds shapes.
  Also (learning loop, v4) mirrors the Elo replay + walk-forward backtest contract and asserts
  it's deterministic, order-independent (sorts by round), rates winners above losers, and keeps
  Brier score in [0,1].
- `validate_learned.py`: assert the `nrl_learned.js` (`window.NRL_LEARNED`) contract — params
  numeric and in sane ranges, all 17 known team shorts present in `elo{}`, backtest fields in
  [0,1] where applicable, `history[]` non-empty with parseable dates, `results[]` well-formed
  with no exact duplicate `round`+`home`+`away`; exit non-zero on failure. Never ship learned
  data that fails this check.
- `README.md`: what it is, how to open, how the model works, how it learns, how weekly refresh
  works.
- `WEEKLY_UPDATE.md`: the exact runbook the scheduled weekly/daily job follows (which URLs to
  fetch, run parser, run `learn_model.py`, run both validators, done).

## Definition of done
Opens offline with no errors; tips computed for the round; Roosters locked; data auto-refreshes
via the weekly job; `validate_data.py` + `validate_learned.py` + `smoke_test.mjs` all pass; the
learned model (`nrl_learned.js`) is only shipped when it validates and respects the
`lowConfidence` guardrail; a non-technical user can understand every screen.
